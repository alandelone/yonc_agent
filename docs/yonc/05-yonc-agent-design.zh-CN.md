# Yonc 项目管理 Agent 设计与补齐清单

日期：2026-09-20  
状态：产品共识已确认；技术方案为建议，尚未实施。  
依据：本次与用户的逐项设计讨论，以及当前本地源码静态核对。本文不代表测试或部署已经通过。

## 1. 目标与边界

Yonc 是用户的项目管理助手，管理用户现在和未来可能要做的事情。保留现有 Canvas、List、Timeline 和拆分 UI，并将 Yonc 接入 UuMA 的 Hermes 专业 Agent 体系。

必须区分两个领域：

| 领域 | 记录什么 | 权威来源 |
| --- | --- | --- |
| Yonc Project Graph | 用户的目标、交付物、工作包、行动、依赖与项目状态 | Yonc 项目后端及其持久化数据 |
| UuMA Workflow / Work Graph | Agent 被安排执行的工作、运行、重试、结果 | UuMA 控制平面 |

用户的项目节点不需要逐一转成 Agent 任务。只有发生实际的 Agent 工作请求，才创建相应运行记录。例如“完成论文实验”是用户项目工作；“协助拆分论文实验”是 Agent 工作。后者完成不能自动完成前者。

Yonc 管理范围覆盖整个项目图，包括查询、拆分、改名、关系调整、讨论排期、进展回顾与追踪。自动后台追踪的触发频率和权限尚未确定，不能由“追踪”推导出持续自主修改。

## 2. 已确认的使用方式

### 2.1 UI：独立的拆分任务

- 对话入口保持在现有「拆分会话」。
- 每个会话围绕选定对象工作，拥有独立目标、消息、草案和生命周期。
- 可以同时存在多个拆分会话，不互相混入聊天或草案。
- 在 Hermes/UuMA 中作为有范围、有结束条件的受委派工作运行。
- 默认仅调整选定对象的拆分结构；读取必要的相关背景不等于获得修改其他项目的权限。
- 需要改变其他项目时先提出建议，经用户明确同意扩大范围后再处理。

### 2.2 Hermes：直接与 Yonc 对话

- 用户可以直接找 Yonc，持续讨论整个项目图。
- 直接对话与 UI 拆分不共享聊天记录。
- 两个入口共享项目数据；可按需查看拆分任务状态、摘要和结果，必要时读取相关记录。
- 不自动把所有拆分聊天灌入直接对话。
- 跨 Agent 派工和运行协调沿用 UuMA Orchestrator 边界；Yonc 不成为另一个全局调度器。

### 2.3 拆分生命周期

- 完成：用户接受具体方案，且方案成功保存到项目图。
- 放弃：用户主动结束，不采用未提交方案。
- 暂离：保留会话与草案，之后继续；关闭页面不等于放弃。
- 生成方案成功、单次模型调用结束，都不等于拆分任务完成。
- 已结束会话保留记录；结束后继续修改的具体交互见待定事项。

## 3. 决策与写入权限

沿用工程原则：Model proposes，Policy authorizes，Business system validates，Runtime commits。

| 情形 | 行为 |
| --- | --- |
| 读取、分析、起草 | 在授权范围内自主执行 |
| 用户明确且无歧义的修改指令 | 校验后执行，不重复索要同一授权 |
| Yonc 主动提出拆分、结构或排期建议 | 保存草案，用户接受后才修改项目图 |
| 对象、值或范围不明确 | 澄清，不猜测写入 |
| 其他 Agent 返回结果 | 记录结果和来源，不自动更改用户项目完成状态 |

接受必须对应实际展示的方案版本。草案自动保存与正式项目提交是不同操作；自动保存不得被解释为接受 Agent 建议。

用户直接编辑正式节点属于明确指令；在拆分草案里编辑卡片属于修改方案，不代表同时接受全部 Agent 建议。建议 UI 清楚显示“草案已保存”和“已提交项目图”两种状态。

## 4. 拆分方法与产出契约

### 4.1 过程灵活

先读取现有节点、子节点及相关背景。已有信息足够就提出草案，关键缺口才提问。支持澄清、讨论选项、局部修订和整体重拆，不要求每条聊天都生成新方案。

可以分阶段停在 L2 或 L3，之后再深入；停止层级不同，但该层级的成果要求不能降低。

### 4.2 成果严格

以下继承现有 `llm_pipeline.py` 的 WBS 定义，并采用本次确认的时间软规则：

| 层级 | 产出要求 | 时间参考 |
| --- | --- | --- |
| L1 Goal | 最终成果，名词短语，符合 SMART | 依项目而定 |
| L2 Deliverable / Module | 主要交付物或模块；名词命名；完整覆盖父级范围，彼此不重叠、不遗漏 | 不新增统一限制 |
| L3 Work Package | 最低交付物层级；名词命名，明确描述交付什么 | 8–80 小时为默认参考 |
| L4 Action | 动词＋名词的实际行动，包含描述与工作量估计 | 不超过 2 小时为默认参考 |

时间超出时说明原因、讨论是否继续细分，不因时长单独判为不合格。成果形式和行动可执行性必须满足。

L4 行动应具备：

1. 明确开始条件，不必另开规划会才能开始。
2. 可观察的完成结果。
3. 单一意图，不把多件独立工作藏在一个行动里。
4. 可控的决策负担，不隐藏重大未决规划。
5. 有边界的工作量；探索工作也需要明确探索范围和输出。

不能用通用句子“完成此任务并交付成果”证明完成标准明确。结构检查通过也不等于语义质量通过。

### 4.3 校验分工（技术建议）

- 后端检查字段、类型、有效引用、父子约束、依赖结构、版本和权限。
- Yonc 审阅实际语义：交付边界、覆盖性、重复、单一意图、未决问题和行动质量，并提供具体理由。
- 语义检查应允许记录“信息不足”，不能把未经检查的项目预置为通过。
- 草案允许不完整；提交前展示未解决问题并完成必要修订。
- 对于语义质量，用代表性案例和人工复核评价；不声称这些性质都能靠确定性代码证明。

## 5. 已有工作与历史

- 默认读取并保留已有子节点，在其基础上增量补充和调整。
- 明确展示新增、修改、建议移除，以及受影响的关系。
- 未出现在草案中的旧节点，不代表用户要求删除。
- 已完成工作必须保留；重新组织也保留其历史和可追溯身份。
- 只有用户明确要求重新拆分时，才提出整体替换方案；整体替换仍不能抹去已完成工作或历史。
- 建议使用显式变更集与可恢复的历史操作，而不是以草案列表覆盖正式子节点集合。

## 6. 运行与集成设计（技术建议，非已实现）

### 6.1 所有权与标识

Yonc 后端保存项目事实、拆分会话和提案版本；Hermes 承载 Agent 推理与对话运行；UuMA 保存执行控制记录。使用 `project_id`、`node_id`、`split_session_id`、`proposal_version` 与 UuMA task/run 标识关联，不合并数据库，也不要求三者生命周期一一对应。

一次人机拆分会话可以持续多天，其中每一轮 Agent 运算是有预算和超时的有限运行；等待用户期间不保持无限模型循环。

建议为每个拆分建立 Mission Contract：目标、允许对象、禁止范围、目标产出层级、验收标准、预算、停止条件和证据引用。预算默认值仍待选定。

### 6.2 对外能力

以语义 API/MCP 提供项目读取、上下文检索、会话消息、草案修订、差异预览、质量检查和受控提交，不暴露任意数据库写入。UI 与 Agent 都经过相同后端规则。

Hermes 的 `yonc` profile、UuMA 注册/路由、受委派运行、权限守卫与部署配置需要共同接入；仅增加提示词不算完成。

UI 卡片编辑和模型回复必须绑定原始会话与提案版本。切换标签页或晚到回复不能写入其他会话。项目被其他会话改动后，提交应重新校验或报告冲突，不能静默覆盖。

### 6.3 工程标准映射

| 工程要求 | 本设计的落实方向 |
| --- | --- |
| Agent 的必要性 | 模型动态决定如何澄清、检索和修订；结构规则仍由代码执行 |
| 持久化状态 | 分离拆分状态、提案状态和 Agent 运行状态，不从聊天猜进度 |
| 权限 | 用户决策来源与执行者分开记录，服务端验证，不信任模型自报授权 |
| 可靠写入 | 统一写入口、版本检查、幂等请求、原子提交与可恢复历史 |
| 恢复 | 超时先查询是否已经提交，再决定重试；暂停、恢复、取消与失败可追踪 |
| 上下文 | 按任务读取最小充分背景，外部内容视为数据，保存来源 |
| 完成证据 | 关联接受记录、提案版本、检查结果、提交批次与变更摘要 |
| 可观测性 | 关联会话、任务、运行、工具、状态变化、耗时、预算消耗及错误 |

工程标准中的运行 DONE 与用户项目节点 DONE 属于不同领域。项目完成指令仍按用户决策权限处理；Agent 运行完成则需要其任务验收证据。

## 8. 建议实施顺序与验收

1. 修正草案/提交边界和旧节点保护，同时落实可靠写入所需基础。
2. 完善分层成果契约、质量审阅、增量差异与接受版本记录。
3. 完善独立会话生命周期和并发保护。
4. 接入 Hermes Yonc、UuMA 运行及权限边界。
5. 执行端到端验收与失败恢复验证。

最低验收场景：

- **AC-01**：AI 生成或修订草案，正式图不变；用户接受指定版本才提交。
- **AC-02**：A、B 两个拆分并行，切换标签页后晚到回复仍归属原会话。
- **AC-03**：Hermes 直接对话可查询项目与拆分摘要，不自动混入 UI 聊天。
- **AC-04**：旧子节点未出现在草案中不会自动删除；已完成节点及历史可追溯。
- **AC-05**：L2/L3 交付物与 L4 行动符合各自标准；套话和空字段不能冒充质量通过。
- **AC-06**：超过参考时长产生说明或讨论，不仅因时长拒绝提交。
- **AC-07**：纯澄清对话不强制改写提案；卡片编辑与模型修订不静默相互覆盖。
- **AC-08**：重复提交不产生重复效果；版本冲突与中途失败不留下部分变更。
- **AC-09**：暂离后恢复同一草案；放弃不写正式图；完成后晚到消息不能继续修改。
- **AC-10**：越出当前拆分范围的建议未经用户授权不能执行。
- **AC-11**：Agent 运行完成不自动完成用户项目；提交记录包含接受和验收证据。
- **AC-12**：提交响应超时先对账；运行取消和预算耗尽可恢复，不丢失已保存草案。

## 9. 尚待确定的实现细节

这些问题不推翻已有产品共识，实施对应功能前再确定：

- UI 到 Hermes 的实际调用桥接方式，以及 UuMA task/run 与拆分会话的映射粒度。
- 已结束拆分再次编辑，是新建关联会话还是显式重新打开；建议新建关联会话，保留原完成记录。
- 接受方案的交互形式：按钮、明确自然语言或两者；均需绑定具体版本。
- 新增、修改、移除建议的部分接受交互，以及建议移除的归档/解除关系语义。
- 预算默认值、语义审阅案例集、项目追踪是否需要后台运行。
