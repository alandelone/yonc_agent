# Yonc Agent 实施与 Hermes 直接部署计划

日期：2026-09-20  
状态：待实施计划。本文创建不代表功能已实现、测试通过或 Hermes 已部署。  
产品基线：[05 设计与补齐清单](05-yonc-agent-design.zh-CN.md)。

## 1. 交付目标

实施完成后，用户能够通过可重复执行的部署入口安装 Hermes `yonc` profile，直接与 Yonc 交谈管理项目图；现有 UI 的多个拆分会话能够分别调用同一个 Yonc 能力，各自保留对话、草案和运行记录。

交付必须同时满足：

- 真实 Hermes profile、UuMA 身份与能力注册、MCP 工具和权限守卫均可工作。
- UI 和 Hermes 访问同一个明确指定的项目数据库，避免无意中生成空库。
- 用户接受前只保存 Agent 草案；明确用户指令按授权执行。
- 已完成工作和历史保留；Agent 运行完成不自动完成用户项目。
- 提供安装、启动、健康检查、更新、故障诊断与回滚说明。
- 部署后完成真实模型和真实工具链的验收，不能以模拟适配器的成功代替。

本次不扩展 Notion 同步、后台自主排期或全局多 Agent 调度。Yonc 的部署不应依赖安装 Scholar、KAG 或硬件实验室组件。

## 2. 目标架构与仓库责任

```text
现有拆分 UI ── Yonc API / 运行桥接 ── UuMA 受控分派 ── Hermes yonc
                                                        ↑
用户直接对话 ────────────────────────────────────────────┘
                                                        │
                                              yonc-project MCP
                                                        │
                                              Yonc 语义 API
                                                        │
                                         校验 / 授权 / 统一写入
                                                        │
                                             Yonc Project Graph

Hermes yonc ── UuMA Worker MCP ── UuMA 运行控制与事件记录
```

建议采用单个 Yonc 后端拥有数据库写入事务，stdio MCP 作为本地语义 API 客户端。模型运行在 Hermes；生产 UI 路径逐步替换原先直接调用 DSPy 的拆分器。确定性适配器仅用于测试或明确标识的离线演示。

| 仓库 | 负责内容 |
| --- | --- |
| `yonc_agent` | 项目规则、迁移、写入历史、拆分状态、运行桥接客户端、MCP、UI、部署入口与使用文档 |
| `UuMA` | `yonc` profile/skills、身份和能力注册、Direct Run、受委派运行、权限守卫、Hermes 配置生成与审计关联 |

UuMA 保持 Agent 运行的唯一控制权。Yonc 仅保存 UuMA/Hermes 标识、关联和必要状态投影，不另建竞争的调度器；既有 AgentRun 设计需据此对齐。

## 3. 关键技术选择

### 3.1 会话与运行分离

- UI 每个拆分使用稳定 `split_session_id`；不同拆分不会复用同一 Hermes 对话标识。
- Hermes 直接对话使用自身独立会话；按需读取项目和拆分摘要。
- 一次长时间拆分由多轮有预算的 Agent 运行组成；等待用户不占用持续循环。
- 运行请求固定绑定会话、父节点、提案基准版本、图版本与幂等标识。异步回复不能依据 UI 当前活动标签决定归属。
- 保存草案、等待用户、接受、提交、完成、放弃与单次 run 的成功/失败分别建模。

### 3.2 授权必须落在服务端

UuMA 当前 specialist 守卫对提交动作有限制。实施时增加明确的 Yonc 域策略，不能关闭守卫或让 Yonc 获得通用 Control MCP。

建议由可信 UI 事件或 Hermes 用户消息入口产生授权凭据，绑定用户、对象、操作内容/方案版本、范围和有效期；模型不能自己提交 `approved=true` 获得权限。

- 明确指令：产生相应用户决策凭据，允许受控执行，无需重复确认。
- Agent 建议：用户接受具体方案后才产生提交凭据。
- 歧义、范围扩大或方案改变：原凭据不能覆盖新动作。
- 专业 Agent 的跨域工作仍交由 Orchestrator；工具结果和外部文本不能形成用户授权。

P0 必须验证 Hermes 可信消息来源及现有 UuMA 审批机制能否承载此凭据。如果版本不支持，应实现受控确认入口；不得以提示词假冒授权。

### 3.3 复用已有可靠写入设计

沿用 [02](02-project-write-and-history.md) 的统一写入、幂等、版本冲突和历史契约，以及 [03](03-runtime-foundation-v1.2.md) 的加法迁移基础。所有旧 API、UI、MCP 的项目写入都经过同一规则入口。不得让新 MCP 安全而旧 API 仍绕过。

## 4. 分阶段工作包

### P0 — 固定集成契约与现状基线

依赖：无。开始时保留两个仓库现有未提交改动；在 UuMA 实施遵循其 AGENTS.md 与 session lifecycle。

工作：

- 核对实际使用的 `YONC_GRAPH_DB`、节点数、schema、服务地址和进程配置。当前存在多个 SQLite 文件，不能按文件名推断正式库。
- 核对已安装 Hermes 的 profile、MCP、`/v1/runs`、会话隔离、取消及网关路由支持；记录版本和可复现探测结果。
- 定义 UI→UuMA→Hermes 的受控入口；Yonc 后端使用窄权限桥接身份，不能将 Orchestrator 凭据发给浏览器或 Agent。
- 明确可信用户授权凭据的来源、消费路径与重试语义。
- 建立 `implementation/features.json`、`implementation/PROGRESS.md`；标记待做、依赖、验收和证据，不预先标完成。

产物：集成契约、数据库基线、部署兼容性矩阵、可执行阶段清单。

完成条件：可用隔离数据发起一次指定 profile 的有限运行，记录结果/取消，并验证不同会话隔离。若不支持，先完成桥接适配再进入正式接入。

### P1 — 可靠项目写入与数据保护

依赖：P0。主要位置：`models.py`、`schema_v2.py`、Alembic、`api.py`、`api_v2.py`、`v2_service.py`；新增/完成 `write_service.py` 及历史服务。

工作：

- 加法迁移、迁移前一致性备份、版本验证、失败恢复；复用 03 的共享迁移函数。
- 统一写入口、原子版本声明、请求去重、用户决策/执行者来源记录、提交证据。
- 将 split 从列表覆盖改为显式变更集，旧节点缺席不触发删除；保留完成节点身份、关系变更证据与历史。
- 补齐可重放记录、冲突感知撤销和恢复基础；盘点并迁移所有项目写入入口。
- 将上下文/运行引用写入关联记录；UuMA 断开时不得虚报运行或项目写入成功。

完成条件：既有 04 中对应 M1–M3 的验收通过；重复请求无重复效果，失败无部分提交，备份恢复可验证，旧完成节点不会因新拆分丢失。

### P2 — 拆分草案、质量与生命周期

依赖：P1。主要位置：`split_adapter.py`、`v2_service.py`、拆分模型及新增 `split_service.py` / `split_contracts.py`。

工作：

- 消息处理区分纯讨论、澄清、检索、修订与提交意图，不要求每条消息生成方案。
- 保留不可变的已接受提案版本；显式保存新增、修改、建议移除和关系差异。
- 固定层级成果要求；L3 8–80 小时和 L4 两小时改为参考提示。
- 取消通用开始条件/完成条件自动补值作为提交通过依据；提供结构检查与有理由的语义审阅结果。
- 已有工作默认增量调整；提供草案持久化、暂离恢复、放弃与完成边界。
- 技术默认：已完成拆分继续编辑时创建关联新会话；接受支持按钮和无歧义自然语言，均绑定版本。
- 首版按完整版本接受；部分接受通过修改草案后重新检查实现，不先引入复杂的逐操作批准系统。

完成条件：设计文档 AC-04–07、AC-09–10 的服务端案例通过，代表性 L2/L3/L4 案例与失败案例有审阅证据。

### P3 — Yonc 语义工具与 Hermes profile

依赖：P1、P2。Yonc 新增 `mcp_project.py`、工具 schema 与 API 客户端；UuMA 新增 `profiles/yonc/SOUL.md` 和相关 skills。

建议工具分组（名称在实现时固定并版本化）：

| 能力 | 操作 |
| --- | --- |
| 读取 | 搜索项目、节点上下文、项目概况、拆分状态/摘要、提交历史 |
| 会话 | 开始/读取/续接拆分、保存消息、记录未决问题、放弃草案 |
| 提案 | 提交草案变更、预览差异、校验、读取质量反馈 |
| 写入 | 用可信用户授权执行明确指令或接受版本，查询写入回执 |

每个工具定义输入输出、权限、超时、错误码、幂等与副作用类型。凭据由进程注入，不能进入提示词；限制检索范围、条数和输出长度。

SOUL 保存身份、项目/运行边界和决策规则；skills 保存上下文读取、灵活讨论、分层成果审阅、接受提交与恢复流程。项目规则仍由后端校验。

完成条件：Hermes 测试 profile 能通过真实 MCP 读图、提出草案、按授权提交；模型伪造身份/授权、外部内容注入和其他 Agent 越权均被服务端拒绝。

### P4 — UuMA 注册、运行与权限集成

依赖：P0、P3。核对并更新以下真实接入点：

- `src/uuma/auth.py`：`yonc` 身份与角色。
- `src/uuma/mcp_worker.py`：专业 Agent 白名单和 Direct Run 路径。
- Agent 能力注册/种子配置、路由与任务契约：完成代码盘点后更新，不能只改 profile 列表。
- `integrations/hermes/uuma_control_guard/`：直接会话注册、域权限、工具白名单、结果处理。
- `src/uuma/specialist_skills.py`：Yonc skills 白名单。
- `scripts/configure-hermes-profile.py`：Worker MCP、`yonc-project` MCP、审计配置与工具限制。
- Orchestrator 身份说明和能力描述：识别何时路由到 Yonc，区分用户项目与 Agent 工作。

通过 UuMA 有限运行承载拆分轮次；保存 `task_id/run_id/external_run_ref` 与 Yonc 会话关联。加入心跳、超时、预算、停止、恢复和结果验收；迟到结果只记录为旧 attempt 结果，不能回退已提交状态。

完成条件：真实直接聊天和 UI 受委派任务均受控注册；成功、失败、取消、等待用户可查询；Yonc 没有通用终端、计算机控制或跨 Agent 自主委派权限。

### P5 — UI 接入与多会话验证

依赖：P2、P4。主要位置：`frontend/src/App.tsx`、`api.ts`、`types.ts` 与新增运行桥接 API。

工作：

- 移除生成回复后的正式图自动提交，改为草案自动保存和明确接受操作。
- 保留已有多个拆分标签；按稳定会话 ID 保存编辑、响应和运行状态。
- 显示思考/工具执行进度、草案保存、待审阅、提交成功及失败重试状态。
- 展示变更差异、质量缺口和时间参考提示；用户可通过聊天或卡片修订。
- 模型回复基于提案版本落地；用户已修改时报告冲突或重新生成，不静默覆盖。
- 关闭页面保存会话；显式放弃才结束；提供停止当前 Agent 运行而保留草案的操作。

完成条件：两个会话并行、切换标签、编辑与模型响应竞争、刷新续接、过期版本接受等端到端测试通过；现有 Canvas/List/Timeline 操作回归通过。

### P6 — 可重复部署、验收与交付

依赖：P1–P5。部署包内容与流程见下一节。

完成条件：在隔离 Hermes profile/测试数据库中完成首次安装和二次更新演练；真实 profile 通过直接聊天与 UI 拆分验收；备份、失败恢复、回滚和现有其他 profiles 保持正常均有证据。

## 5. 部署交付设计

### 5.1 需要新增的入口

以下为计划交付文件，当前尚不存在或尚不具备所述能力：

- Yonc `scripts/deploy-hermes.ps1`：统一入口，接受 Yonc/UuMA/Hermes 路径、Python、数据库路径和本地服务端口。
- Yonc `scripts/start-yonc.ps1`：启动并检查本地后端/UI，隐藏后台进程窗口，记录进程与日志位置。
- Yonc `scripts/check-hermes-deployment.ps1`：核对 profile、工具、权限、schema、数据库身份与端到端探针。
- Yonc `scripts/rollback-hermes-deployment.ps1`：恢复部署清单中的配置和兼容应用版本。
- Yonc `docs/yonc/07-hermes-deployment-runbook.zh-CN.md`：安装、直接聊天、UI、更新、诊断、卸载/回滚说明。
- UuMA：从现有全量 `deploy-hermes.ps1` 提取可复用的按 profile 配置能力，支持仅部署 `yonc`，不触发其他专业 Agent 的强制依赖检查。

配置遵循一个明确来源：`YONC_GRAPH_DB`、Yonc API 地址、UuMA 地址/身份、Hermes executable/profile、模型/provider 继承策略。新增 API 地址环境变量与参数名称在 P0 固定。

### 5.2 安装顺序

1. 只读 preflight：运行时依赖、Hermes 能力、UuMA 兼容版本、数据库真实路径、磁盘空间、端口和已有服务。
2. 建立部署清单与备份：代码版本、schema、配置、profile 管理段和数据库一致性备份，不输出秘密。
3. 安装固定版本依赖并构建 UI；加入 MCP 所需依赖与可重复安装配置，避免依赖当前机器偶然已有库。
4. 迁移并验证项目库；不得静默切换到空库，也不得导入遗留 Notion 数据作为隐式安装步骤。
5. 启动或复用匹配数据库的 Yonc 本地服务，健康检查必须返回数据库身份和 schema。
6. 注册 UuMA `yonc` 能力，安装 profile、skills、MCP 和 guard/audit 插件。复用 provider 设置并保留用户自定义；移除继承而来的无关工具与凭据。
7. 校验生成配置，执行一次受控 Hermes gateway 重载/重启，随后检查现有 profile 和 Yonc 路由。
8. 执行隔离测试项目的真实读、草案、接受和写入验收，输出可操作的启动方式、UI 地址、版本和日志路径。

默认只监听 loopback。现有 Yonc 默认 8765，而 UuMA 文档指出该端口可能已被 WSL Relay 占用：必须探测并要求配置可用端口，不能抢占或默默连接错误服务。UuMA 文档中的 8766 也要实际校验。

### 5.3 更新与回滚

- 二次部署应幂等：不重复注册、不覆盖自定义 SOUL、不重建数据库、不重置其他 profiles。
- 托管配置冲突保存待合并文件并报告，避免覆盖用户改动。
- 配置回滚与数据回滚分开。更新后已有新项目写入时，不直接用旧备份覆盖；先校验向后兼容或采用恢复/补偿流程。
- 任一步失败不宣告部署完成；报告已完成步骤、恢复路径和可重试下一步。
- 卸载仅移除本次托管 profile/配置和进程，不删除项目库、历史或用户自定义文件。

## 6. 验证与发布门槛

| 类别 | 必须保留的证据 |
| --- | --- |
| 数据 | 新库/旧库迁移、备份、失败恢复、重复启动与历史重建 |
| 权限 | 明确用户指令、接受具体版本、伪造授权、过期授权、跨范围拒绝 |
| 并发 | 两会话隔离、过期版本、重复请求、晚到响应、编辑冲突 |
| 质量 | L2/L3/L4 正反例、覆盖/重复检查、套话拒绝、软时长处理 |
| 恢复 | 提交后响应丢失的对账、Agent 取消、预算耗尽、进程重启 |
| 部署 | 首次安装、幂等更新、配置保留、端口冲突、回滚、其他 profiles 回归 |
| 真实体验 | Hermes 直接聊天；UI 两个独立拆分；接受后图更新且任务可追溯 |

所有 [05 的 AC-01–12](05-yonc-agent-design.zh-CN.md#8-建议实施顺序与验收) 应映射到测试或人工验收记录。服务端业务测试与 UI 构建/端到端检查均通过后才进入真实部署验收。生产项目只读核对，测试写入使用隔离数据。

发布完成意味着用户可以按交付说明直接选择 `yonc` 开始聊天，UI 拆分也走真实 Hermes 链路；仅生成 SOUL、发现 MCP 工具或部署脚本退出成功都不够。
